# PR 7: respond.io attachment transport

Carry attachments between respond.io and the agent without changing ACP channel behavior.

- Keep ACP v1 content blocks as the one internal content shape. Extend the existing core types only for ACP media and resource metadata that this work needs. Do not add respond.io content types to the core.
- Keep the ACP channel as pass-through and preserve each ACP v1 shape: an image has data, MIME type, and an optional URI; audio has data and MIME type; an embedded resource has its URI and optional MIME type inside `resource`; and a resource link has URI, name, optional MIME type, and optional size.
- Add only the missing ACP fields to the shared core shape: embedded-resource MIME type and resource-link size. Do not add fields to content types that ACP v1 does not define.
- Convert only at the respond.io edge. A respond.io attachment maps to an ACP resource link, and an outbound ACP block with a usable public URL maps to a respond.io `attachment` message with type `image`, `video`, `audio`, or `file`.
- Put the smallest conversation-file contract in `internal/core`. The contract saves a named stream for a conversation and returns its safe name and URI. The agent-side conversation directory owner implements it, `channel.Build` qualifies the conversation name before use, and channel factories receive the contract. respond.io must not import agent packages, read `data_dir`, call harness methods, or build agent directory paths.
- Save every attachment from an incoming respond.io `message.received` event that Momo owns in that conversation's directory before the agent turn starts. The agent receives one ACP resource link for each saved file.
- Accept attachment download URLs only with an `http` or `https` scheme. Apply the same rule to every redirect target.
- Follow redirects without resetting the per-file byte limit. Reject a declared `Content-Length` above the limit before writing, stop a stream when it exceeds the limit, and count the bytes from the response body rather than trusting the declared size.
- Add `max_attachment_bytes` to the respond.io channel settings. Its default is `20,000,000` decimal bytes per file. Reject a configured value that is not positive.
- Keep the existing webhook body limit separate from `max_attachment_bytes`. The webhook handler must verify and acknowledge a valid event before it downloads an attachment.
- Write each download to a temporary file in the target conversation directory. Rename it only after a complete download within the limit. Remove the temporary file after an HTTP error, redirect error, read error, size error, write error, or cancelled download.
- Treat every remote filename as untrusted. Remove directory parts, control characters, empty names, `.` and `..`. Keep the final path inside the conversation directory, do not follow a file path out through a symlink, and do not overwrite an existing file. Generate a unique safe name when the proposed name is unsafe, empty, or already used.
- Set the resource link name to the saved basename. Use provider name and MIME metadata when the webhook supplies them, then HTTP `Content-Disposition` and `Content-Type`, then the final URL path and its extension. Use `application/octet-stream` when no MIME type is known. Include the stored byte count in the ACP resource link.
- If an attachment URL is absent or invalid, the download fails, the response is not successful, the file is too large, or storage fails, still run the owned conversation's agent turn. Replace that attachment with a plain ACP text block that says the attachment is unavailable and gives its safe display name and a short reason.
- Errors should be surfaced to the channel as usual.
- Map an outbound ACP image with an HTTP(S) URI by its image MIME type. Map ACP resource links by their MIME type and embedded resources by `resource.mimeType`: `image/*`, `video/*`, and `audio/*` use those attachment types, and every other MIME type uses `file`.
- If an outbound block has no MIME type, classify its HTTP(S) URI from the case-insensitive extension in the parsed URL path. Ignore query text and fragments. Use Go's known MIME extension table. A known non-media MIME type maps to `file`.
- A typed media or resource block without a usable HTTP(S) URI cannot form a respond.io attachment payload. This includes every ACP audio block because ACP v1 audio has no URI. Return a delivery error instead of dropping the block or sending base64 data as a URL. Keep upload or hosting of data-only ACP media out of PR 7.
- Find absolute HTTP(S) URLs in outbound ACP text blocks. Classify each URL only from its parsed path extension with the same MIME rules. Never request a plain text URL to inspect its headers or content. Keep a URL with no known extension as text.
- Replace each classified media or file URL in mixed text with one attachment send at that position. Send non-empty text before and after it as text messages. Preserve block order and URL order, and do not include adjacent punctuation in the URL.
- Make one respond.io API call for each ordered text or attachment part. Use `{ "message": { "type": "attachment", "attachment": { "type": "<type>", "url": "<url>" } } }` for an attachment. Do not start the next call until the current call succeeds.
- Stop an outbound sequence at its first invalid typed block or failed respond.io API call. Return the error so the existing turn failure report adds one internal comment. Do not retry or roll back parts that respond.io already accepted.
- Write tests before production code. Start with failing cases for inbound image, video, audio, and file payloads, ACP resource-link metadata, safe and duplicate filenames, unsupported URL schemes, redirects, declared and streamed size limits, partial-file cleanup, download failures and unavailable markers, webhook acknowledgement before download, typed outbound blocks, mixed text with several URLs, query strings and punctuation, unknown extensions left as text, ordered sends, and stop-on-first-failure behavior.
- Add pass-through tests for ACP media and resource metadata. Add contract and wiring tests that prove respond.io uses a qualified conversation file store without access to agent or configuration internals.
- Update the README configuration sample and respond.io guide with `max_attachment_bytes`, its decimal-byte default, saved-file location, accepted URL schemes, inbound failure behavior, outbound URL classification, ordering, and the limits on data-only blocks.
- Files likely touched: `internal/core/core.go`, a new `internal/core` conversation-file contract and tests, `internal/agent/agent.go`, `internal/agent/harness.go`, and their tests for safe conversation storage, `internal/channel/channel.go` and `internal/channel/channel_test.go` for factory wiring and qualification, `internal/channel/acp/acp.go`, `internal/channel/acp/methods.go`, and ACP tests for the shared contract and metadata pass-through, `internal/channel/respondio/respondio.go`, `internal/channel/respondio/client.go`, and their tests, `cmd/momo/main.go` and `cmd/momo/main_test.go` for wiring, and `README.md`. `internal/config` should not need a source change because respond.io owns and strictly decodes its settings.
- Exclude attachment upload or hosting, data-only ACP media conversion, content sniffing, malware scanning, retention policy, total conversation storage quotas, webhook body-limit changes, changes to ACP transport behavior, and media context for contact, operator, or workflow messages while another assignee owns the conversation.
- Base implementation only on this file and the current tracked source. Do not use closed pull requests, deleted work, git history, or the stale respond.io-only file list in `PR-PLAN.md`.
